# 同类项目研究与横向对比（competitor-research）

这不是"列几个 star 高的仓库"，而是**回答三个问题：别人怎么做的、我们差在哪、能抄什么（合法地）**。

---

## 1. 找谁比（选样标准）

优先级从高到低：
1. **功能重叠度**：解决同一类问题（同在 `topic:` 下，或描述里的核心名词一致）
2. **仍在维护**：近 12 个月有提交，近 24 个月有发版
3. **工程质量**：有测试、有 CI、有文档，代码可读
4. **规模匹配**：优先"比我们稍强"的项目，巨型项目（>100k star）只在架构上有参考价值
5. **可借鉴性**：功能可拆解、许可证兼容

**排除**：awesome-*、教程合集、面试题库、书籍代码、`roadmap`、`cheatsheet`、纯模板脚手架、已归档项目。

**数量**：主力对比 ≥5 个，条件允许 8–10 个。少于 5 个必须解释原因（如"该领域公开项目极少"），不能凑数。

---

## 2. 怎么找（检索式）

```
topic:<核心topic>                            # 最准
"<核心功能词>" in:description language:<lang>
<项目名> alternatives site:github.com        # 网页搜索补充
topic:<相邻topic>                            # 上下游/替代方案
```

拿到候选后，**必须打开仓库**看：README、目录结构、`package.json`/`pyproject.toml`、核心模块 1–2 个文件。只看 star 和描述的对比表是废的。

---

## 3. 每个项目要采集的 8 项

| 项 | 从哪看 | 用来判断 |
|---|---|---|
| 技术架构 | 目录 + 依赖 + 入口 | 分层是否清晰、是否同栈 |
| 核心功能 | README 功能清单 + 源码验证 | 功能是否真的存在（别信 README 吹） |
| UI 水平 | 截图/在线 demo/组件目录 | 是否值得借鉴视觉与交互 |
| 自动化能力 | `.github/workflows`、脚本、CLI | CI/CD 与发布成熟度 |
| 工程质量 | 测试目录、lint 配置、类型覆盖 | 是否可作为代码范本 |
| 性能设计 | 缓存/并发/分页实现 | 有无可直接借鉴的方案 |
| 许可证 | `LICENSE` | 能否复用代码（关键！） |
| 风险点 | 未解决 issue、安全隐患 | 不要学它的坑 |

---

## 4. 许可证兼容矩阵

| 对方许可证 | 读代码学思路 | 复制代码到 MIT 项目 | 复制到闭源商业项目 |
|---|---|---|---|
| MIT / BSD / Apache-2.0 | ✅ | ✅（Apache 需保留 NOTICE） | ✅（保留版权声明） |
| MPL-2.0 | ✅ | ⚠️ 被修改文件需开源 | ⚠️ 同上 |
| LGPL | ✅ | ⚠️ 动态链接可，静态链接需开源 | ⚠️ 谨慎 |
| GPL-2.0/3.0 | ✅ | ❌ 会传染 | ❌ |
| AGPL | ✅ | ❌ 网络服务也传染 | ❌ |
| 无许可证 | ✅ | ❌ 默认保留所有权利 | ❌ |
| 自定义/NOASSERTION | ✅ | ❌ 需人工确认 | ❌ |

**结论固定句式**：
> 可以借鉴 `X` 的**设计思路**（算法/交互/数据结构），但 `Y` 项目为 AGPL-3.0，**不可复制其代码**；若需相同能力，应基于 `Z`（MIT）实现或自行编写。

**绝不能**因为"只是抄一小段"就忽略许可证。

## 5. 对比表（必须写到报告里）

```markdown
| 项目 | 技术架构 | 核心功能 | UI 水平 | 工程化 | 值得借鉴的地方 | 许可证 |
|---|---|---|---|---|---|---|
| [owner/name](url) | React+TS+Vite | 多标签、插件市场 | 高（有设计系统） | CI+单测+自动发版 | 插件沙箱隔离方案 | MIT |
```

"值得借鉴的地方"必须是**具体的机制**，不是"UI 好看"。

---

## 6. 差距分析的四问

1. **别人有我们没有** → 功能缺口（进第 13 节）
2. **我们有别人没有** → 差异化优势（要在结论里讲，不能只讲缺点）
3. **都有但别人做得更好** → 改造项（进第二阶段路线图）
4. **别人踩过的坑** → 风险预警（避免重复投入）

---

## 7. 推荐引入的开源库（要给理由和代价）

| 场景 | 推荐 | 理由 | 代价 |
|---|---|---|---|
| 表单校验 | zod / pydantic | 声明式 + 类型推导 | 增加包体积 |
| 重试与退避 | tenacity / p-retry | 避免手写重试逻辑 | 需统一异常类型 |
| 结构化日志 | structlog / pino | 便于检索与采集 | 改造现有日志调用 |

**每条必须写**：解决什么具体问题、许可证、包体积/依赖代价、是否与现有栈冲突。

---

## 8. 不建议引入（也要写）

有些功能看着好但不该做：
- 与项目定位不符（把 CLI 做成 GUI）
- 维护成本 > 收益（自建插件市场）
- 依赖重（为一个小组件引入 200KB 库）
- 许可证风险

写清"不建议 + 原因"，比无脑堆功能更专业。

---

## 9. 反造假纪律

- 每个被引用的项目必须附 `https://github.com/owner/repo` 真实链接
- 功能描述必须来自实际读到的 README 或源码，不能凭名字猜
- star 数、许可证必须是查到的真实值（记录查询时间）
- 检索失败要写"检索词 X 未返回有效结果"，**不许虚构项目名**
