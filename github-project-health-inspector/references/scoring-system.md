# 评分体系（scoring-system）

100 分制。**分数是结论的摘要，不是结论本身**——每个分数必须能倒推回具体证据。

---

## 1. 权重表（合计 100，不得改动分母）

| # | 维度 | 权重 | 核心问题 |
|---|---|---|---|
| 1 | 代码质量 | 15 | 会不会经常出 bug？ |
| 2 | 安全性 | 15 | 会不会被攻破？ |
| 3 | 功能完整度 | 15 | 能不能满足目标用户的主流程？ |
| 4 | 性能表现 | 10 | 规模上来会不会垮？ |
| 5 | UI/UX | 10 | 用起来顺不顺？ |
| 6 | 架构设计 | 10 | 加功能会不会越来越难？ |
| 7 | 工程化 | 10 | 协作与发布是否可靠？ |
| 8 | 文档质量 | 5 | 新人能不能上手？ |
| 9 | 可维护性 | 5 | 半年后还敢改吗？ |
| 10 | 开源生态与维护情况 | 5 | 项目会不会突然死掉？ |

**UI/UX 不适用时**（无图形界面）：该维度标 `N/A`，把 10 分按比例摊到 代码质量/功能完整度/工程化（分别 +4/+3/+3），并在评分表中显式写出调整，**不能不解释就改分母**。

---

## 2. 评分锚点（每档都要能举例）

### 代码质量（15）
| 档位 | 特征 |
|---|---|
| 13–15 | 命名清晰、分层合理、错误处理完整、有单测覆盖核心逻辑、无明显重复 |
| 10–12 | 整体可读，少量长函数/重复，异常处理基本到位 |
| 7–9 | 存在多处长函数、复制粘贴、吞异常，但主流程可读 |
| 4–6 | 大量重复、魔法值、全局状态、错误静默 |
| 0–3 | 无法阅读/逻辑混乱/大量死代码 |

### 安全性（15）
| 档位 | 特征 |
|---|---|
| 13–15 | 无高危，输入校验与鉴权完整，依赖无已知 CVE，CI 权限收敛 |
| 10–12 | 无高危，但存在若干中危或加固项 |
| 7–9 | 1 个高危但利用条件苛刻，或有系统性的加固缺失 |
| 4–6 | 存在可直接利用的高危（RCE/注入/凭据泄漏） |
| 0–3 | 多个 P0 并存，或核心凭据已泄漏 |

**硬规则**：存在 1 个 P0 → 安全性不得高于 8 分。

### 功能完整度（15）
| 档位 | 特征 |
|---|---|
| 13–15 | 主流程闭环 + 边界场景 + 错误恢复，功能与宣称一致 |
| 10–12 | 主流程可用，缺次要功能或边界处理 |
| 7–9 | 核心功能能用但关键场景缺失（如无导出、无权限管理） |
| 4–6 | 只能演示，无法实际使用 |
| 0–3 | 主要功能不可用 |

### 性能表现（10）
| 档位 | 特征 |
|---|---|
| 9–10 | 有实测数据支撑，指标良好 |
| 7–8 | 结构上无明显瓶颈，或少量可控问题 |
| 5–6 | 存在 N+1、无缓存、大包等明显问题但未到不可用 |
| 3–4 | 有会随规模恶化的设计缺陷 |
| 0–2 | 已知会卡死/OOM |

**硬规则**：未实测 → **上限 7 分**，且必须标注"静态推断，未实测"。

### UI/UX（10）
见 `ui-ux-audit.md` 第 6 节。未实测上限 6 分。

### 架构设计（10）
| 档位 | 特征 |
|---|---|
| 9–10 | 边界清晰、依赖单向、易扩展、无循环依赖 |
| 7–8 | 分层基本合理，局部耦合 |
| 5–6 | 模块职责模糊，改一处牵连多处 |
| 3–4 | 上帝类、循环依赖、业务与框架深度耦合 |
| 0–2 | 无结构可言 |

### 工程化（10）
| 档位 | 特征 |
|---|---|
| 9–10 | CI 跑测试+lint+构建，自动发版，有 issue/PR 模板、dependabot、CODEOWNERS |
| 7–8 | 有 CI 与基本规范，缺自动发版或依赖更新 |
| 5–6 | 有构建脚本但无 CI，或 CI 形同虚设 |
| 3–4 | 手动构建，无测试流程 |
| 0–2 | 无构建脚本/无法构建 |

### 文档质量（5）
| 档位 | 特征 |
|---|---|
| 5 | README 有定位/安装/快速开始/配置/FAQ，示例可跑 |
| 4 | 有安装与用法，缺配置或示例 |
| 3 | 只有简介，安装说明不完整 |
| 1–2 | 几乎无文档或已过期 |
| 0 | 无 README |

### 可维护性（5）
看：类型覆盖、模块大小、注释质量、命名一致性、测试可回归性、上手成本。

### 开源生态与维护情况（5）
| 档位 | 特征 |
|---|---|
| 5 | 近 3 月有提交，定期发版，issue 响应快，多贡献者，社区活跃 |
| 4 | 半年内有更新，有发版节奏 |
| 3 | 一年内有更新，维护者单一 |
| 1–2 | 超过一年无更新，或大量积压 issue |
| 0 | 已归档/事实停更 |

## 3. 不确定性处理（关键）

某个维度证据不足时，**三步走**：

1. **降权**：按"最坏可见证据 + 明确标注不确定"打分，不给满分
2. **标注**：评分表加脚注 `*`，并在第 19 节说明缺什么证据
3. **区间**：允许给区间（如 `9–11/15`），但综合分取**区间下限**

示例：
> 性能表现 `6/10`\* — 静态分析发现 3 处 N+1 查询，但项目缺少可运行环境（无 `.env.example` 必需项、依赖含私有包），**未做实测**，故按可见证据封顶 7 分并取 6。

**禁止**：证据缺失却给 12/15 并说"看起来不错"。

---

## 4. 综合分与等级

| 区间 | 等级 | 含义 |
|---|---|---|
| 90–100 | 优秀 | 可直接用于生产，可作为同类标杆 |
| 80–89 | 良好 | 生产可用，有明确改进点 |
| 70–79 | 合格 | 能用，但存在需要计划修复的问题 |
| 60–69 | 需要改进 | 有影响使用的缺陷，谨慎采用 |
| 0–59 | 存在较大问题 | 不建议生产使用 |

**总分 = 各维度得分之和**，四舍五入到整数。校验器会核对这个等式，别手改。

---

## 5. 一票否决项（总分上限）

| 情况 | 总分上限 |
|---|---|
| 存在未修复的 P0（RCE/凭据泄漏/任意文件读写） | 59 |
| 无法构建/无法安装 | 65 |
| 已归档或 24 个月无提交 | 70 |
| 无许可证（法律上不可用） | 75 |
| 核心功能不可用 | 60 |

写明"因 X，总分封顶 59"，不要偷偷扣分。

---

## 6. 分数怎么写才可信

```markdown
| 维度 | 得分 | 满分 | 主要依据 |
|---|---|---|---|
| 代码质量 | 11 | 15 | 4 处长函数（`cli.py:1022` 等）、1 处裸 except、重复率 1.1%，整体分层清晰 |
| 安全性 | 12 | 15 | 无硬编码凭据；2 处 eval 属设计内使用（配置加载），需文档警示；依赖无自身锁定版本，未能验证 CVE* |
| 性能表现 | 6 | 10 | 无实测环境；发现 3 处循环内查询* |
| **合计** | **78** | **100** | 等级：合格 |
```

依据列必须包含**数字或文件路径**，不能写"较好/一般"。
